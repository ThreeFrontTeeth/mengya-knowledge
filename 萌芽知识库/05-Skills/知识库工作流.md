# 知识库工作流

这是本库的操作手册，不是自动安装的 Agent Skill。首次整理样例见 [LLM Wiki](../06-Wiki/概念/LLM%20Wiki.md)；持续验证状态只在 [知识库使用验证](../01-进行中/知识库使用验证.md) 维护。授权边界统一遵循 [AGENTS.md](../AGENTS.md)，日期与资源位置统一遵循 [日期规范](../06-Wiki/资料进入与日期规范.md)。

## 先选这次要做的事

先读首页和有关的进行中记录，明确用户关心的问题、材料范围与预期产物。信息足够就直接使用，不重复询问，也不默认所有材料都服务于同一领域。

| 用户意图 | 完成边界 |
|---|---|
| 只保存、收集资料 | 保存来源和附件、去重、记录待整理状态；不声称已形成知识 |
| 整理或更新知识 | 读取来源与旧页，综合后更新正文、引用、相关入口与处理状态 |
| 回答问题 | 查索引、读有关页面、核对来源，按问题选择文字、对比表或图示；写回按授权处理 |
| 检查知识库 | 报告具体缺口、矛盾和引用问题；修复按已确认范围执行 |

“整理这份资料”可连贯完成保存与整理，不要求用户为每一步重复发指令。来源内容没有变化只表示无需重复保存，不代表一定无需重新整理：未完成处理、旧结论有误、出现新问题或关联时仍要复核。

## 把当前文件夹搭建成知识库

可以直接说：

> 请参考这个仓库：https://github.com/ThreeFrontTeeth/mengya-knowledge，为当前文件夹搭建知识库，配置目录结构、AI 工作规则和使用流程，并整理已有文章的归属与结构。保留已有内容和顶层文件夹名称，不额外套一层同名文件夹；你能判断的先给出归类建议，无法确定的集中问我，涉及移动或改写时先让我确认具体方案。

搭建包括梳理已有文章、配置入口与规则，不以创建目录或下载模板作为全部完成。沿用当前文件夹自己的名称；已有同等用途的目录先考虑复用。参考本库的结构与方法，不照搬本库个人记录、示例状态或历史备份。

### 先检查，再判断

先查当前目录、已有规则、索引和状态记录，再按需阅读文章、来源信息及附件引用。已有规则保留并按需补充，不能直接用模板覆盖。根据实际内容和明确状态判断用途，不能只按标题、篇幅或最后修改日期认定是否完成。

| 内容与依据 | 建议归属 |
|---|---|
| 零散想法、随手记下但尚未推进的问题 | 灵感库 |
| 明确仍在写、仍在学习，有未完成步骤或下一步的内容 | 进行中 |
| 用户确认完成，或有可信定稿、已发布记录的完整文章、脚本、读书笔记 | 成品库 |
| 从外部收集的原文、摘录、截图和附件 | 外部资源；保留来源与原件 |
| 明确已结束或暂停的过程与进度记录 | 历史记录；最终作品与仍有效的知识不随之搬走 |
| 可复用的操作方法、步骤和提示词 | Skills |
| 围绕长期问题整理、有来源并需要持续更新的知识 | Wiki；优先更新已有主题 |

同一主题可以有进行中的草稿、成品和 Wiki 页，但不复制同一正文来凑目录。比如读书笔记仍在补充时放在进行中，确认整理完成后进入成品库；值得长期维护的概念再按需提炼到 Wiki，保留关联。

### 拿不准的集中问用户

先列出“当前路径、建议位置、判断依据、待确认点”。有明确证据的无需逐篇询问分类；不能判断的集中提出，每轮优先问一到三个影响实际处理的问题，附具体文件名和建议。例如：

- “这两篇视频脚本还会继续修改，还是已经定稿？这会决定放在进行中还是成品库。”
- “这份学习记录暂时不继续了，还是准备接着学？我需要确认是保留在进行中还是归入历史记录。”
- “这篇笔记同时有外部摘录和你自己的总结，要保留为一篇完整笔记，还是拆出原始资料、用链接关联？”

不要问用户仅凭文件即可确认的信息，也不为凑问题而提问。用户纠正后按其实际用途调整；未得到答案的文件保留原位、标为待确认，可以继续检查其他文件，但不能用等待超时替代答案。

### 把归位和正文调整分开

1. **文件归位**：列出原路径、目标路径、归属依据、相关附件与引用，以及同名冲突。按已确认的方案移动，不能以覆盖解决冲突。
2. **正文结构**：逐篇检查标题层级、段落顺序、来源区和关联链接是否需要调整。先说明具体改法、保留范围和理由，不为了统一格式重写所有文章；原始资料正文不改写。拆分、合并或改写用户笔记须明确列入方案，不能因同意归类就视为同意改写。
3. **规则与导航**：按实际内容建立或更新首页、领域入口和工作规则，修复移动引起的相对链接、图片引用与双向链接。目录或标题中使用用户自己的知识库名称。

按 [执行与授权](../AGENTS.md#执行与授权) 展示具体范围、影响和恢复方式；已确认部分直接执行，超出范围的再确认。修改前备份并保留原路径，恢复时只处理本轮改动，避免覆盖之后的新内容。

完成后核对文件数量、原文保留情况、附件和引用、索引入口及用户确认的归属；如有正文调整，逐篇核对语义与来源。报告实际完成项、待确认文件及未运行的验证。只有目录就绪时不能称已有文章已经整理完成。

## 整理资料

可以直接说：“把这份资料整理进知识库，优先更新已有主题，保留出处。”

1. 读取材料和来源说明，确认作者、原链接、日期、正文完整性、附件读取范围。遇到缺失，只处理能可靠读取的部分。
2. 按原链接及内容检查是否已收集，再查当天收集记录。已处理且无新内容的重复输入直接引用原结果，不创建副本，不制造更新时间。
3. 按 [分领域管理](../06-Wiki/分领域管理.md) 判断主要问题和领域，搜索已有领域入口、主题名、同义词及别名。领域来自实际内容，不固定为示例中的分类。写正文前形成简短的证据与改动清单：来源要点、已有覆盖、冲突或缺口、目标页面、受影响页面、新增/更新/跳过的理由。只展示结论与依据，不输出冗长推演；拿不准的集中询问，已授权且明确的继续执行。
4. 读相关旧页面，将新证据整合进对应段落。有独立阅读价值才另建来源摘要或分析；不要求一条输入生产多页。
5. 引用支持的具体结论，保留关键案例与条件。新来源改变旧判断时检查链接到该主题的分析、进行中内容和成品；成品是否修订按其版本规则处理。改动涉及重要判断时，给出“原结论、拟改内容、理由、来源”的对照；不清空重写整页来掩盖变化。
6. 检查新旧页面的入链和出链，再更新相关领域首页、知识首页、收集记录和日志。收集记录链接实际产物，并说明未覆盖部分；Wiki 正文引用具体原文，两边形成可追溯关系。部分处理要列出缺失内容及已完成页面，不能提前标为已整理。

多份资料一起进入时，先去重并按共同问题分组，再综合更新相关页面。可以分批完成，但每批标清处理范围与未完成项；不因单篇来源重复就漏掉新的跨来源关系。

## 知识页怎么写

默认一页回答一个可长期复用的问题。新领域内容先按领域组织，概念、实体或分析子目录在有需要时再建；已有页面保持稳定路径。中文名称优先，常用英文词记录为 aliases。领域归属、跨领域引用及可选 domains 字段统一见 [分领域管理](../06-Wiki/分领域管理.md)。

元数据至少记录 created、updated、type、status、aliases。正文至少交代：核心结论、解释或案例、来源与适用边界。没有内容的小节不要保留占位文字。verified 只在实际核对时添加，并注明范围；不要求手填容易失真的来源数量。

建议的段落次序：先回答问题，再解释为什么，然后给必要案例，最后说明局限和关联。来源在对应段落就近放链接；可以另列证据表，但不能让读者猜每条来源支持哪句话。参考 [实际概念页](../06-Wiki/概念/LLM%20Wiki.md)，不用每次复制固定长模板。

章节随问题变化：概念页讲定义与原理，工具页讲用途与限制，事件页交代时间与背景，对比页统一比较条件，方法页解释步骤与代价，总览页组织主题关系。只在材料足够时使用，不预建类型目录、不强加新元数据。篇幅服从理解需要；一个页面包含数个可独立回答的问题、难以导航时才提出拆分，并保留原入口与引用。

对综合判断核对反例、不同适用条件和证据缺口。有实质分歧就写清依据与不确定性；没有读到反方证据时如实说明，不编造“平衡观点”。保留来源独立性，转载和复述不算新增佐证。

冲突记录包含：争议点、旧依据、新依据、各自日期与条件、当前判断、还缺什么证据。这里只规定处理方式，不创建虚构冲突充数。

## 回答问题与沉淀

可以说：“根据知识库回答这个问题。”这默认只读。

需要保存时说：“把这次有价值的新理解补回相关知识页。”

先从知识索引定位相关领域和页面，必要时沿关联跨领域查找，再核实关键原文。回答尽量先用短结论，随后给证据和边界；库中不足则明确说明。是否查外部资料取决于问题与时效要求。

写回前判断新意：已有内容只链接；对旧结论有补充就更新原页；跨主题形成独立判断才新建分析页。不能把整段聊天记录当作知识，也不能把 AI 回答本身当作独立来源。本次写回样例见 [维护取舍](../06-Wiki/分析/萌芽知识库的维护取舍.md)。

## 检查知识库

可以说：“检查知识库，先报告问题。”默认只读；已授权修复的范围可以直接处理。

| 检查 | 怎么判断 | 不能夸大的结果 |
|---|---|---|
| 文件链接 | 链接目标存在，路径移动后引用同步；有锚点时核实标题 | 文件存在不代表章节或内容正确 |
| 孤立页面 | 知识页有索引入口；有意义的相关主题相互关联 | 不为凑连接数量乱加链接 |
| 领域归属 | 入口可达、名称一致；跨领域通过链接复用，同名概念核对含义 | 不把用户举例当作固定领域，也不强行归类 |
| 重复内容 | 比较标题、别名和所回答的问题 | 同名或文本相似仅是候选，不能自动合并 |
| 来源 | 关键事实有可定位出处，来源实际支持结论 | 有网址不等于有证据 |
| 冲突与时效 | 核对定义、条件、日期和相反证据 | 静态脚本不能判定所有事实真假 |
| 处理状态 | 已整理来源确有产物，部分处理有缺失说明 | “下载成功”不能算“整理完成” |
| 关联影响 | 旧判断变化后，检查引用它的分析和成品 | 链接正常不能保证关联结论已更新 |
| 来源覆盖 | 收集记录能找到实际整理产物；待整理、部分处理与暂不处理有依据 | 没有 Wiki 产物的来源不一定是错误，可能尚未处理或没有独立价值 |
| 待确认事项 | 查看本次任务记录中未解决的归类、冲突和拆分问题 | 不把用户未回答视为默认同意，也不重复创建另一份待办清单 |
| 知识缺口 | 找到反复出现但解释不足的问题、缺少证据的结论与相关旧页 | 不能仅靠词频、连线数量或日期认定知识缺失或失效 |

完成一次资料处理后检查受影响范围；需要全库检查时由用户触发，不默认设置定时任务。输出具体文件、问题、依据、修复建议与未核实范围。遇到新问题再扩展检查，不做无意义反复扫描。

## 从缺口到补充研究

查询或检查发现缺口时，先指出具体问题、涉及页面、现有证据不足在哪里，再给出少量有针对性的研究问题及优先来源。用户已要求研究或补齐的，在该范围内检索；未授权扩展工作时只给建议，不无限抓取资料。

取得可读取的有效来源后，按收集、综合、引用检查流程补入已有知识，并回到最初的问题检验是否得到回答。仍然缺证据就保留未解决状态；搜索命中、保存网页或增加页数都不代表缺口已补齐。

## 来源变化与引用依赖

来源有新版时另存版本，比较实际改变的论点，查找直接引用、来源汇总和关联页面，再判断哪些结论受影响。来源链接失效不等于论点为假；正文日期较旧也不等于内容过时。

用户要求删除或撤回来源时，先列出依赖页面与结论，并给出恢复方式。只有这一份依据的结论需要补证、降为待核实或经确认撤除；有其他独立来源的结论逐条保留。不能自动删除整篇 Wiki，也不能只删来源链接而保留无依据的断言。删除按明确授权执行。

## 日志怎么记

沿用 [更新记录](../06-Wiki/更新记录.md)，新条目使用 `## [YYYY-MM-DD] ingest | 标题`，类型还可用 query、lint、maintain。记录来源或任务、改动页面、关键变化、验证结果和未完成项。旧日志不重写。

只有发生实际整理、写回或维护才追加持久日志。纯问答与无变化的重复检查不自动写日志。总首页最多展示近期几项重点，完整历史留在日志；知识首页为当前页面保留链接和一句说明。

## 从知识到创作

开始创作时先从 Wiki 找观点、案例与原始依据，在进行中形成草稿；确认完整后进入成品库。正文按口播节奏组织，但数字、引语和产品能力仍需核实。成品的来源与修订约定见 [成品入口](../02-成品库/成品入口.md)。
