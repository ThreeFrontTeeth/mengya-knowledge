# 萌芽知识库的维护取舍

本页回答：吸收卡帕西的方法后，萌芽知识库现在应该做什么，什么可以等一等？以下结论是结合本库状态的设计判断，不是第三方效果测评。概念背景见 [LLM Wiki](../概念/LLM%20Wiki.md)。

## 当前采用的方式

保留七个已确认目录。收集日期帮助回忆“什么时候看到的”，主题页帮助回答“这个问题是什么”；两种入口通过链接连接，不需要将同一主题按天复制。

把操作步骤集中到 [工作流](../../05-Skills/知识库工作流.md)，执行边界留在 [AGENTS.md](../../AGENTS.md)，路径与日期留在 [日期规范](../资料进入与日期规范.md)。这些文件分别回答不同问题，首页只做导航，不再重复整套说明。

优先用已有来源做真实内容，再决定是否增加设施。是否需要搜索工具，以实际漏检、查找耗时和索引维护负担判断，不能只用文件数量作统一门槛。

## 对原文各项建议的本地取舍

下表的原文位置可在 [本地完整原文](../../03-外部资源/2026/2026-09-05/网页/卡帕西原始方案/llm-wiki.md) 回查；采用方式由本库决定。

| 原文位置或提及项 | 本库如何处理 | 以后何时调整 |
|---|---|---|
| Architecture | 复用外部资源、Wiki、AGENTS.md，沿用现有名称 | 实际职责重叠时再调整 |
| Operations | 用一份手册串起整理、问答沉淀和检查 | 用真实相关资料持续验证 |
| Indexing and logging | 复用知识首页和更新记录，新日志使用统一类型 | 导航过长再按主题拆分，不提前分库 |
| Optional: CLI tools / qmd | 当前不安装，先用索引和文本搜索 | 已出现索引无法解决的检索问题，并核实工具后再评估 |
| Obsidian Web Clipper | 本次未安装或测试采集扩展 | 网页采集成为经常任务时实测正文及图片完整性 |
| 本地图片 | 沿用每份资源自己的附件位置，阅读时单独查看需要的图片 | 实际导入图文时验证；不照抄未经本机验证的快捷键 |
| Graph view | 内容之间先建立有意义的链接 | 有足够主题后用客户端检查关系，不以图形美观验收知识质量 |
| Marp | 当前不增加演示文稿链路 | 有实际幻灯片交付时选工具 |
| Dataview | 知识页保留少量元数据，当前不用插件生成表格 | 手动导航难维护时再验证查询配置 |
| Git | 本次使用修改前 ZIP 和改动清单恢复 | 用户明确要求后再配置版本管理，不擅自提交或推送 |
| Note | 按个人用途取舍，原文提到的选项不必全部安装 | 用具体问题推动迭代 |

上述工具只记录原文中提及的名称与本库取舍，没有验证其当前版本能力。

## 为什么不自动保存每次回答

日常提问有大量重复解释和临时假设，全部写入会增加噪声。本库以是否带来新的证据、解释或跨主题关系决定保存价值；在用户授权沉淀时更新，单纯查询保持只读。

## 为什么知识更新不直接重写成品

Wiki 维护当前理解，成品代表某次完整表达。一个事实变化可能让教程需要修订，也可能只影响其中一段；先标出影响，依据任务授权修订，保留之前的版本及日期。规则见 [成品入口](../../02-成品库/成品入口.md)。
